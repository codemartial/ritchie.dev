Automatic Concurrency Arrives in Ritchie

Ritchie figures out when to overlap network calls to save time.

Tahir Hashmi · 19 November 2026

On this page
  1. 01.What's New
  2. 02.Automatic Concurrency
  3. 03.Under the Hood
  4. 04.The Road Ahead

It's been six weeks of gruelling R&D here at ritchie.dev. The headline feature that got delivered is Automatic Concurrency, but under the hood, it required so much work that we ended up rewriting the compiler from scratch — for the fourth time!

Let's take a look at what it took to get here.

What's New

  1. Automatic Concurrency! Ritchie compiler figures out which operations can be executed concurrently to save wall time over blocked I/O. You get this benefit without having to write explicit forks, async/await, promises, futures, etc.
  2. RITE was thoroughly revised and rigorously checked. It is now in a shape where it can be used as an abstract machine and architecture that we can build against and match or exceed, but not fall short of.
  3. The error handling model was revised to decouple it from concurrency. Previously concurrency was enabled only inside a handled block. Now Automatic Concurrency is always on, independent of error handling syntax.
  4. Much more compact and competent Ritchie Skill for coding agents.
  5. A new Ritchie at a Glance page for you to get familiar with the language.

Under the Hood

The compiler rewrite was undertaken with great deliberation after we started seeing a whack-a-mole pattern of errors, which pointed to a weakness in design. We were not convinced that we could build something as complicated as Automatic Concurrency on a weak base. So here's how the design was strengthened.

Ritchie now has an intermediate representation (IR) that we call ritchie-min or kernel, interchangeably. Many Ritchie features were already implicitly specified as rewrites into a subset language (how a += b is exactly a = a + b, to take the simplest example). However, this subset language was only "in the head" and the implementation often short-circuited it.

Coming up with a formal specification of the kernel language allowed us to:

  • more rigorously specify high level features in terms of lower level behaviour
  • verifiably prove that those features were indeed implemented as lowering rewrites
  • design the runtime model in terms of the kernel language semantics and prove correctness over a smaller subset

This, crucially, allows us to switch from Go to another backend language for code generation at some point. Perhaps the biggest reason for doing this would be the memory model mismatch between Ritchie and Go. However, the speed of development with the Go compiler, its extensive standard library and its concurrency and networking capabilities put that rewrite quite far into the future.

Working through these changes also led us to start running "evals" for Ritchie coding with agents. While it's too early to officially publish benchmark numbers, we can reveal that:

  • we have over four thousand Ritchie programs generated and saved on disk and multiples of that being written and thrown away during design and development.
  • Ritchie code generation in terms of token usage is already competitive with mainstream languages.

The Road Ahead

Automatic Concurrency is the first of many whole-program automations that are in scope for Ritchie and its runtime. With the new architecture in place, we can aim for greater automation in resilience, resource management and runtime optimisation.

The best way to see where it's headed is to try it: head over to the Playground, throw your trickiest sequence of remote calls at it, and see what Ritchie does with them.
