Ritchie's features look conventional on the surface, but they have slight twists that combine with each other to yield a smoother development process. That gets you to "done correctly" faster. The not so secret sauce is that Ritchie is designed for an abstract machine that is a distributed system rather than one computer.

Let's take a short trip with Ritchie against the reigning productivity champion, TypeScript, to see what that buys.

Let's Go Online Shopping!

Say you're building an online shopping checkout flow. You have three APIs as building blocks.

The Unhappiness Guards

Good product design always pays attention to unhappy situations and failures as much as successes. We add the following safeguards:

  1. Pricing goes down. When Pricing has an outage, we charge the list price. Anything else Pricing complains about is the caller's problem.
  2. Products get discontinued. Pricing or Inventory can report that a product is gone, and the customer should hear about it either way.
  3. The Ledger fails. The connection to the Ledger can drop after the write has gone out. The sale may have happened, and a blind retry could charge the customer twice, so the response is "reconcile" and something has to reconcile it later.

TypeScript needs nested try blocks because once an error is raised, there is no reaching back into the code that raised it. There are now twice as many lines for error checking as for successful functionality. So much for a simple checkout!

Ritchie only goes from 7 to 11 lines. Crucially, the happy path is still clearly consolidated, so it's a lot easier to follow the business logic while reading Ritchie compared to TypeScript.

Ritchie handles the pricing fallback inline. An unhandled error bubbles up to the caller, so for "anything else" there's nothing more to write. That includes Discontinued!, which reaches the caller without us writing a line for it. The runtime reports the lost ledger write as its own error, Unverified!.

This is one step ahead of TypeScript already, because the Ritchie runtime tracks how far a write got, even inside the Ledger. If the call failed before the Ledger reached the point where it actually writes, the error is Unmodified! instead of Unverified!. So the Ritchie program starts a (definitely slow, potentially manual) reconciliation only when it really can't be sure.

The SREs Have a Say

Things were going swimmingly for a month, until last week a stuck dependency took checkout down. The SREs now have a rule: every call runs under a time budget, and a checkout that runs out of it responds instead of hanging.

Ritchie's change is a grand total of one line vs. 6 for TypeScript.

Deadlines are built into the runtime, so there is nothing to thread through your code. Every entry already runs its calls under a budget, 1400 ms unless configured, and holds back an extra buffer to deliver the response. Every remote call inherits what is left of it. Honestly, this would've been a zero-code change if we hadn't decided to rename the error from Cancelled! to OutOfTime!.

TypeScript has to thread the deadline by hand, and every call must remember to carry it. Leave { signal } off one of them and that call ignores the budget, and the compiler has no opinion on the matter. A deadline that lapses while the Ledger write is in flight falls into the same catch as a dropped connection, so it raises Reconcile, which is the answer for an issued write that may or may not have completed.

Time for a Reckoning

A customer buys four things. We run the TypeScript first, with a 1400 ms budget.

Half a cart. No service failed. Every one responded on time, and every handler did its job, including the one that had to give up. Here is where the 1400 ms went.

The price of b has nothing to do with the price of a, and neither has anything to do with how many are left on the shelf, yet each read stood in line behind the last one, because every await stops the function until its response arrives. This cart needs 2400 ms of calls, and a twenty-item cart would need twelve seconds. Most of that time is spent waiting for responses that the next call had no use for. The Ledger is the only thing here that has to stay in line.

So the reads have to go out together.

Rewiring the TypeScript

We know how to do this. It is what async was for. Our list of demands is short:

  1. Every read starts at once.
  2. Writes still happen one at a time, in cart order.
  3. Every failure rule from before keeps its meaning.
  4. Nothing is left running after the function has responded.

A good TypeScript programmer reaches for Promise.all first, wrapping each line so that a discontinued product becomes a value and only a real surprise rejects. It is tidy, and it is fine until one read is slow, because nothing can be written until the slowest read in the cart has responded. Give line 4 a Pricing call of 1000 ms, and line 1, which had everything it needed at 300 ms, does not write until after 1000 ms. The budget runs out and the response is total $3, reconcile 1.

So each line has to write as soon as it is ready, in cart order. That means starting reads in one place and awaiting them in another, and Promise.all cannot do that. We build it by hand.

It works. It responds in 700 ms, and outages, lost responses and deadlines all come out as promised. However, the code has almost 50% additional line-count without any new logic about shopping.

Function Colouring. async has been on this function since line one, and every caller of it has been paying the same tax. Now the colour has reached the data. price used to be a number, and it is now a Promise<number> until someone awaits it, so it goes in reads[i]!.price and its type has to be kept in mind wherever it is needed. It has reached the callbacks as well, because the reads now start inside a map, each with a .catch of its own.

The handlers moved. A try around a call used to protect that call. A promise fails where it is awaited, so the fallback for a 503 had to leave the loop and go to a .catch inside a map, while the check for a 410 stayed behind in a second loop. One loop became two, one to start things and one to wait for them, and the rule for a single item of the cart is now spread across both.

Two lines you'd better not miss. Look at price.catch(() => {}) and stock.catch(() => {}). They do nothing, and they are there because a promise that rejects while nothing is awaiting it ends the process. Delete them and a discontinued product on line 3 takes the server down, along with every other customer on it. tsc --strict accepts the program either way.

We wrote the cleanup. An AbortController, a merged signal and a finally now exist only to stop reads that a line further down might no longer want.

That is the state of the art.

But wait. How does Ritchie know that it can send every price and stock read right away, yet has to send the ledger writes one at a time? That's the Automatic Concurrency feature of Ritchie in action. It does two things that we had to do manually in TypeScript:

Dataflow. A remote call is sent where it is written, and the program waits for its response at the first place that needs to look inside it. @Pricing.quote(sku) and @Inventory.check(sku) need only a sku, and nothing that an earlier line of the cart computes, so the loop sends them ahead for every iteration and eight reads get dispatched at once. @Ledger.record(sku, price) needs a price, so it has to wait for that response. And price is still a Decimal in the source instead of some futuristic template with a promise.

Effect Tracking. The compiler marks every method that has externally observable effects, such as changing remote state, and every method that calls such a method, all the way up. An unmarked call is a read, and a read can be thrown away: if the program turns out not to need it, it is cancelled and nothing has changed. A marked call cannot be taken back. So it starts only after everything written above it that could stop it has responded, and marked calls go one at a time, in written order.2 That is why the Ledger stays in line, and why a sold-out item does not reach it.

Your handlers did not move either, because a failure takes effect at the statement that made the call, whatever time its response turns up.

To go fast, TypeScript had to change almost half the code. Ritchie did not change at all. It was never slow.

Erm, Actually...

This is where someone says, "try language X instead", or "use framework Y".

So, we also wrote the fast checkout in Kotlin and Go, in case TypeScript was the problem. It wasn't. Kotlin took 47 lines and Go took 54, and each one had lines that break the program if you leave them out, but that the compiler won't miss.

Yes, we know about Effect, and we know about Encore. It is the best TypeScript has, so let us judge it on what is left: reading it and trusting it.

Now for trust. Here is every guarantee Ritchie gave us along the way, held up against Encore and Effect.

GuaranteeRitchieEncore + Effect
An unhandled rejection cannot crash the serverYesYes
An unhandled error reaches the callerYesExplicit coding required
The compiler knows which errors each call can raiseYesExplicit coding required
Every call runs within a time budgetYes, alwaysExplicit coding required
An abandoned read receives a cancellation signalYesExplicit coding required
External effects are not observed ahead of timeYesExplicit coding required
The response waits for every writeYesExplicit coding required
A failed write can confirm whether nothing was modifiedYes, Unmodified! is built-inNot built in

Wherever the right-hand column requires explicit coding, tsc --strict accepts the program with that code left out, and therefore without the guarantee. Ritchie won't save you from every mistake, but its guarantees are not yours to forget.

If you're going to write it in someone else's language3 anyway, try Ritchie. It means business.
